1. บทนำ (Introduction)

1.1 วัตถุประสงค์ (Purpose)

เอกสารฉบับนี้เป็นข้อกำหนดความต้องการของซอฟต์แวร์ (SRS) สำหรับการสร้างระบบใบแจ้งซ่อม (Request Repair System) ขึ้นใหม่ (rebuild/clone) จากระบบเดิมที่ใช้งานบน UAT พร้อมทั้ง (1) ปรับรหัสสถานะเป็นมาตรฐานใหม่ 3 หลักที่อ่านง่ายและไม่กระโดดข้ามไปมา และ (2) ขยายขีดความสามารถตามหลักการบริหารศูนย์ซ่อม ได้แก่ ประเภทการให้บริการ (Service Tier: Normal / Express / VIP), ค่าเปิดเครื่องตรวจเช็คตามประเภทสินค้า (Diagnostic Fee), การคิดใบเสนอราคาจากต้นทุนบวกกำไร (Cost-Plus Quotation) และการบันทึกการชำระเงิน (Payment Recording)

1.2 ขอบเขต (Scope)

ระบบครอบคลุม lifecycle ของใบแจ้งซ่อมตั้งแต่ CS เปิดงานรับสินค้าจากลูกค้า, GR รับสินค้าและเลือกเส้นทางซ่อม (DC Path / Vendor Path), การตีราคาและขออนุมัติจากลูกค้า, การซ่อมและส่งคืนสินค้า, จนถึงลูกค้ารับสินค้าคืนพร้อมลายเซ็นดิจิทัล รวมถึงงานบริหารระบบ (Admin): จัดการผู้ใช้, ข้อมูลอ้างอิง, SLA และรายงาน

1.3 ระบบเดิม (Existing System)

ระบบเดิมเป็น Next.js (React) + REST API + Prisma ORM, deploy ที่ http://10.77.3.87:2001 (UAT) ยืนยันพฤติกรรมจากการทดสอบด้วยผู้ใช้ทดสอบ 4 บทบาท (test_cs / test_gr / test_dc / test_am) เมื่อ 17/07/2026 ประกอบกับกฎทางธุรกิจจากไฟล์ BUSINESS_RULES.md ของ source code เดิม เอกสารฉบับนี้ใช้รหัสสถานะมาตรฐานใหม่เป็นหลัก โดยกำกับรหัสเดิม (legacy) ไว้ในตาราง mapping หัวข้อ 3.2 และมี SQL migration script แนบแยกไฟล์

3. Status Model และ Flow การทำงาน

3.1 แผนภาพ Flow ทั้งระบบ (รหัสมาตรฐานใหม่)

สีพื้นหลัง = ผู้รับผิดชอบดำเนินการ:    เหลือง = CS    ฟ้า = GR    เขียว = DC    เทา = ปิดงาน

← เลือก DC Path (สถานะ 200)     |     เลือก Vendor Path (สถานะ 300) →

ทุกสถานะ: ยกเลิกได้ (สถานะ 000 ตามเงื่อนไข FIX-02) · Rollback ถอยทีละขั้นพร้อมเหตุผล · ทุก action บันทึก transaction_log

3.2 มาตรฐานรหัสสถานะใหม่และตาราง Mapping

รหัสสถานะใหม่เป็นตัวเลข 3 หลักเสมอ ออกแบบให้อ่านความคืบหน้าได้จากตัวเลขโดยตรง:

หลักร้อย = เฟส/เส้นทาง: 0 = ยกเลิก, 1 = รับเข้า (ใช้ร่วมกันทุกเส้นทาง), 2 = DC Path, 3 = Vendor Path

หลักสิบ = ลำดับขั้นตอน เพิ่มทีละ 10 (เว้นช่องว่างไว้แทรกสถานะใหม่ในอนาคตโดยไม่ต้องต่อหลัก)

หลักหน่วย = variant: 0 = ขั้นตอนปกติ, 5 = ทางเลือกคู่ขนานของขั้นตอนเดียวกัน (เช่น 270 ไม่ซ่อม / 275 ซ่อมเสร็จ), 9 = ปิดงาน (299, 399)

ความสมมาตรสองเส้นทาง: ขั้นตอนเดียวกันใช้หลักสิบใกล้เคียงกัน เช่น ตีราคา = 240/310, ขออนุมัติ = 250/320, ปิดงาน = x99

การ migrate ข้อมูลเดิม: ใช้ script แนบ status_code_migration.sql (สร้างตาราง mapping แล้ว update ทุกตารางที่อ้างรหัสสถานะภายใน transaction เดียว)

3.4 ตารางสถานะและ SLA (ค่าจากหน้า Maintain ของระบบจริง)

3.5 กติกาการเปลี่ยนสถานะ

สถานะเดินไปข้างหน้าทางเดียว (forward-only) ยกเว้นการ Rollback ซึ่งถอยได้ทีละขั้นตาม Rollback Map และต้องระบุเหตุผลเสมอ

GR เป็นผู้เลือกเส้นทาง: update เป็น 200 = DC Path, update เป็น 300 = Vendor Path เมื่อเลือกแล้วเปลี่ยนไม่ได้ (ยกเว้น rollback กลับ 110) ระบบมี validation เตือนหากสินค้าไม่อยู่ในรายการจัดส่งผ่าน DC (ยืนยัน override ได้ — พบจากการทดสอบจริง)

DC ตีกลับสินค้า (Reject): rollback จาก 210/220/230 จะ set reject_flg="Y" + reject_from_status, ล้างข้อมูล DC และลบ attachment ของ step 220

ยกเลิกใบแจ้งซ่อม: set status = 000 ระบบเดิมไม่มี validation ว่าสถานะปัจจุบันยกเลิกได้หรือไม่ — ระบบใหม่ต้องจำกัดตาม FIX-02 (ดู 10)

ทุกการเปลี่ยนสถานะบันทึก transaction_log (ผู้ทำ, IP, ข้อความ, step, request) และ DB trigger อัพเดต status_updated_date เพื่อคำนวณ SLA

3.6 Rollback Map (รหัสใหม่)

หมายเหตุ: 290→275 คงพฤติกรรมเดิม (236→235) คือถอยข้ามขา 280/285 กลับไปจุด Vendor ส่งคืน และ 350/360 ไม่อยู่ใน rollback map ตามระบบเดิม

4. กฎทางธุรกิจเดิมที่ต้องคงไว้ (Core Business Rules)

4.1 การออกเลขที่เอกสาร (Running Number)

เลขที่ใบแจ้งซ่อม: {BU}{StoreNick2}{YY}{MM}{DD}{RUN4} เช่น TWBN2607160004 (BU=TW, สาขา=BN, ปี พ.ศ. 2 หลัก) สร้างแบบ concurrent-safe ด้วย upsert + increment บนตาราง running_doc

เลขที่ใบคืนสินค้า: {BU}R{StoreNick2}{YY}{MM}{DD}{RUN4} ออกเมื่อลูกค้ารับสินค้าคืน

4.2 เอกสารแนบ (Attachments)

เปิดงานต้องแนบรูป Serial Number และรูปสินค้า (บังคับทั้งคู่) ตั้งชื่อไฟล์ {request_no}_{prefix}_{timestamp}{ext}

ทุกจุดส่งมอบ (CS→GR, GR→Vendor, Vendor→DC ฯลฯ) มีฟอร์มบันทึก ผู้ส่งมอบ/ผู้รับ/วันที่/เบอร์ติดต่อ + ไฟล์แนบบังคับ (ยืนยันจากการทดสอบทุกฟอร์ม)

4.3 ใบเสนอราคาและการอนุมัติ (Quotation & Customer Approval)

Mode ของ Quotation ต้องตรงกับ path: DC Path → mode "DC" (สถานะ 250–275), Vendor Path → mode "VEN" (สถานะ 320–345)

ลูกค้าอนุมัติ/ไม่อนุมัติเป็นรายรายการ (user_repair_flg Y/N + เหตุผล) และมีผลสรุปรวม user_approve_flg

ผลอนุมัติกำหนดสถานะถัดไป: อนุมัติ (Y) → 275 (DC) / 345 (Vendor), ไม่อนุมัติ (N) → 270 / 340

4.4 การแจ้ง Vendor (Vendor Notification)

เมื่อสินค้าพร้อมให้รับ ระบบส่งอีเมลอัตโนมัติ: SKU → vendor_name (commodity table) → vendor_email (vendor_info table) พร้อมลิงก์หน้า print {APP_URL}/print/{requestId} หน้า Maintain มี import/export รายชื่อ Vendor + email

4.5 การส่งคืนของ Vendor (3 ช่องทาง)

คืน GR โดยตรง → 360 | คืนผ่าน DC แทนสาขา → 350 → DC ส่งต่อ → 360 | เส้นทาง DC มาตรฐาน → 280

4.6 การปิดงานและลายเซ็น (Closing & Digital Signature)

ลูกค้ารับสินค้าคืนต้องเซ็นอิเล็กทรอนิกส์ (signature canvas → Base64 → JPEG → attachment) พร้อมออกเลขที่ใบคืนสินค้า (สถานะ 299/399)

4.7 อื่น ๆ

internal_flg = "Y" สำหรับสินค้าของพนักงาน/ลูกค้าภายใน

Dashboard: การ์ด KPI 6 ชุด (ทั้งหมด, รอการซ่อมแยก CS/GR/DC, กำลังซ่อม, รอลูกค้ารับคืนแยกอนุมัติ/ไม่อนุมัติ, ส่งมอบแล้ว, ยกเลิกแยกลูกค้า/ร้านค้า) กรองรายวัน/สัปดาห์/เดือน

รายการงานมีตัวชี้วัด On Track / At Risk / Critical พร้อม progress bar ของแต่ละสถานะ และ Export Excel

5. Functional Requirements (ระบบเดิมที่ต้อง Clone)

5.1 Authentication

FR-AUTH-01 Login ด้วย username/password, แสดง error เมื่อกรอกไม่ครบหรือ credential ผิด

FR-AUTH-02 Redirect ตาม role, ซ่อน/disable เมนูที่ไม่มีสิทธิ์ (พบจริง: ปุ่มเปิดใบแจ้งซ่อมเป็นสีเทาสำหรับ GR/DC)

FR-AUTH-03 Session expiry + Logout ทุกหน้า, RBAC ต้องบังคับที่ API ทุก endpoint ไม่ใช่แค่ frontend

5.2 CS

FR-CS-01 ฟอร์มเปิดใบแจ้งซ่อม 2 ส่วน: รายละเอียดลูกค้า (ชื่อ*, นามสกุล*, ที่อยู่, โทรศัพท์*) และรายละเอียดสินค้า (checkbox สินค้าอยู่ในระบบ → lookup SKU/Barcode, SKU*, Barcode*, ประเภทสินค้า*, ยี่ห้อ (filtered), รุ่น, Serial, ไฟล์รูป Serial*, จำนวน*, วันที่รับสินค้า*, อาการที่พบ*, ปัญหาที่เกิด: ในประกัน/นอกประกัน*, ไฟล์แนบ*)

FR-CS-02 บันทึกแล้วออกเลขที่ใบแจ้งและเข้าสถานะ 100 จากนั้น CS บันทึกการส่งสินค้าให้ GR (ฟอร์ม ผู้ส่งมอบ/ผู้รับ/วันที่/เบอร์/ไฟล์แนบ)

FR-CS-03 รายการสถานะ: ค้นหา, Filter, Export Excel, Edit (สถานะต้น ๆ), ยกเลิกพร้อมเหตุผล, ปุ่มดำเนินการตามสถานะที่ตนรับผิดชอบ

FR-CS-04 ขออนุมัติราคาจากลูกค้า (250/320), บันทึกผลอนุมัติรายรายการ (260/330), รับสินค้าคืน (290/390), ส่งมอบลูกค้าพร้อมลายเซ็น (299/399)

5.3 GR

FR-GR-01 รับสินค้าจาก CS (สถานะ 110) แล้วเลือกเส้นทาง: ปุ่ม "จัดส่งให้ DC" / "จัดส่งให้ Vendor" พร้อม dialog ยืนยันเมื่อสินค้าไม่อยู่ในรายการ DC

FR-GR-02 บันทึกรายละเอียด Vendor มารับสินค้า (ผู้ขาย*, ผู้มารับ*, วันที่ส่ง*, เบอร์*, ไฟล์แนบ*)

FR-GR-03 รับสินค้าคืนจาก DC/Vendor (280→285, 350→360) และส่งต่อให้ CS

5.4 DC

FR-DC-01 รับสินค้าจากสาขา (220), ตีกลับได้กรณีไม่ตรง/ไม่ครบ, บันทึกส่งให้ Vendor (230), รับคืนจาก Vendor (ฟอร์ม ผู้ส่งมอบ/ผู้รับ/วันที่รับคืน/เบอร์/ไฟล์แนบ)

5.5 ADMIN — Maintain

FR-AM-01 Status Info: แก้ไข SLA (ชั่วโมง) ของทุกสถานะ กรองตาม Path (ทั้งหมด/DC/VENDOR)

FR-AM-02 Vendor Info: รายชื่อ Vendor + email, มี Template / Import / Export

FR-AM-03 (ระบบใหม่) จัดการผู้ใช้, สาขา, ประเภทสินค้า, ยี่ห้อ, ค่าเปิดเครื่อง, margin, service tier — ดูหมวด 6

6. ส่วนขยายใหม่ (New Features — Service Center Best Practices)

ออกแบบตามแนวปฏิบัติของศูนย์บริการซ่อม โดยฝังเข้ากับ flow เดิมโดยไม่เพิ่มสถานะใหม่ (ใช้ field/flag และตารางใหม่แทน) เพื่อลดผลกระทบต่อ state machine

6.1 ประเภทการให้บริการ (Service Tier: NORMAL / EXPRESS / VIP)

เลือกได้ตอนเปิดใบแจ้งซ่อม (FR-CS-01) เก็บใน field service_tier ของ repair_ticket และแสดง badge ในทุกรายการงาน

Business Rule ST-1: tier มีผลต่อ deadline = status_updated_date + (SLA × tier_multiplier) และตัวชี้วัด On Track / At Risk / Critical

Business Rule ST-2: เปลี่ยน tier ได้เฉพาะก่อนเข้าสถานะตีราคา (240/310) และต้องบันทึก transaction_log พร้อมเหตุผล

Business Rule ST-3: Dashboard เพิ่มตัวกรองและ KPI แยกตาม tier (จำนวนงาน, SLA compliance, รายได้ surcharge)

6.2 ค่าเปิดเครื่อง / ค่าตรวจเช็คเบื้องต้น (Diagnostic Fee ตามประเภทสินค้า)

เรียกเก็บ ณ วันเปิดใบแจ้งซ่อม (เฉพาะงานนอกประกัน — งานในประกันยกเว้นโดย default, config ได้) อัตราค่าเปิดเครื่องกำหนดต่อประเภทสินค้าในหน้า Admin ตัวอย่างโครงสร้างอัตราเริ่มต้น:

Business Rule DF-1: สร้าง payment transaction ประเภท DIAGNOSTIC_FEE + ออกใบเสร็จทันทีที่รับชำระ ก่อนสถานะ 100 → 110

Business Rule DF-2: ถ้าลูกค้าอนุมัติซ่อม ค่าเปิดเครื่องถูกหักออกจากยอดค่าซ่อมสุทธิ (แสดงเป็นส่วนลดในใบเสนอราคา/ใบเสร็จ)

Business Rule DF-3: ถ้าลูกค้าไม่อนุมัติซ่อม ค่าเปิดเครื่องไม่คืน (นโยบาย default — config เป็นคืนบางส่วนได้) ต้องแจ้งลูกค้า ณ วันรับเครื่องและพิมพ์เงื่อนไขบนใบรับเครื่อง

Business Rule DF-4: งานในประกันไม่เก็บค่าเปิดเครื่อง แต่ถ้าตรวจแล้วพบว่าความเสียหายอยู่นอกเงื่อนไขประกัน (เช่น ใช้งานผิดวิธี) ระบบให้ CS แปลงงานเป็นนอกประกันและเรียกเก็บย้อนหลังก่อนเริ่มซ่อม

6.3 ใบเสนอราคาแบบต้นทุนบวกกำไร (Cost-Plus Quotation)

ขยายตาราง quotation เดิม: Vendor แจ้งต้นทุน แล้วระบบคำนวณราคาขายอัตโนมัติจาก margin ที่ config ต่อประเภทสินค้า/tier ก่อนส่งขออนุมัติลูกค้า

Business Rule QT-1: margin ต่ำกว่า floor (default 15%) หรือ discount เกินเพดาน ต้องผ่านการอนุมัติภายใน (Admin/Supervisor) ก่อนส่งลูกค้า — บันทึก approver ใน transaction_log

Business Rule QT-2: ลูกค้าเห็นเฉพาะราคาขาย ไม่เห็นโครงสร้างต้นทุน; สิทธิ์เห็น cost/margin จำกัดที่ GR/DC/Admin

Business Rule QT-3: คงกฎเดิม — อนุมัติรายรายการ, mode ตรงกับ path, ผลอนุมัติกำหนดสถานะ 270/275 หรือ 340/345

Business Rule QT-4: เก็บประวัติทุก revision ของใบเสนอราคา (quotation_version) เพื่อตรวจสอบย้อนหลัง

6.4 การบันทึกการชำระเงิน (Payment Recording)

เพิ่มตาราง payment_transaction ผูกกับใบแจ้งซ่อม รองรับการชำระหลายครั้งต่อใบงาน

Business Rule PM-1: จุดเก็บเงิน — ค่าเปิดเครื่อง/Express surcharge เก็บตอนเปิดงาน (CS), ยอดค่าซ่อมคงเหลือเก็บก่อนส่งมอบสินค้า (สถานะ 290/390 → 299/399 จะเดินต่อได้ต่อเมื่อยอดค้างชำระ = 0)

Business Rule PM-2: หน้าจอส่งมอบสินค้าแสดงสรุป: ยอดใบเสนอราคา − ค่าเปิดเครื่องที่ชำระแล้ว − ส่วนลด + VAT = ยอดต้องชำระ พร้อมประวัติการชำระทั้งหมด

Business Rule PM-3: งานที่ยกเลิกหลังชำระค่าเปิดเครื่อง → ไม่คืนเงิน (default ตาม DF-3); งานยกเลิกโดยความผิดของร้าน → สร้าง REFUND ได้ภายใต้สิทธิ์ Supervisor

Business Rule PM-4: รายงานเงินสดประจำวันต่อสาขา (daily cash reconciliation) แยกตาม method และผู้รับชำระ + export Excel

9. Non-Functional Requirements

Performance: โหลดหน้า < 2 วินาที (LAN), API list < 500ms (paginated ≤ 100 แถว), upload ≤ 10MB/ไฟล์, รองรับ ≥ 50 concurrent users

Security: bcrypt (cost ≥ 12), HTTP-only session cookie/JWT, RBAC ที่ API ทุกเส้น, validate MIME server-side, เก็บไฟล์นอก web root, HTTPS, input sanitisation; ข้อมูลเงิน (cost/margin) ต้องจำกัดสิทธิ์การอ่านที่ API layer

Reliability: อัพเดตสถานะเป็น atomic transaction, uptime 99.5% เวลาทำการ, error boundary ครอบทั้ง app (แก้ BUG-03 เดิม)

Usability: ภาษาไทยเป็นหลัก, พ.ศ. ใน date picker, responsive ≥ 768px, inline validation, เครื่องหมาย * ชัดเจน

Maintainability/Scalability: Git, .env, Prisma migrations, OpenAPI 3.0, stateless API, object storage (MinIO/S3), connection pooling
